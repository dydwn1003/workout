# Adapt (가칭) — 적응형 칼로리·체중 코치

체중 정체기에도 목표 칼로리를 알아서 다시 맞춰주는 코치 앱입니다.
체중과 식사를 기록하면, 추세 체중 변화와 섭취량으로 **실제 소비량(TDEE)을 역산**해서 매주 목표를 조정합니다.

- Flutter (iOS / Android / Web), 한국어·영어
- 오프라인 MVP: 기기에 로컬 저장, 서버 없음
- 디자인: 크림 배경 + 파스텔 포인트 컬러, 둥근 카드, 코드로 그린 복숭아 마스코트, 나눔스퀘어라운드 폰트, 부드러운 이징 애니메이션

## 바로 실행하기

```bash
scripts/run_web.sh          # Flutter 설치(없으면) → 웹 빌드 → http://localhost:8080
scripts/run_web.sh --dev    # 핫 리로드 개발 서버
```

- 첫 화면에서 동의 체크 → **"샘플 데이터로 먼저 둘러보기"** 를 누르면 5주치 기록이 채워지고, 주간 체크인을 바로 체험할 수 있어요.
- 모바일: `flutter run` (에뮬레이터/실기기 연결 시).
- Claude Code: `.claude/settings.json`의 SessionStart 훅이 Flutter SDK를 준비하고, `launch-app` 스킬이 실행·스크린샷 방법을 알려줍니다. "앱 실행해줘"라고 하면 됩니다.

### Claude Code에서 바로 보기 (설치 없이)

`preview/adapt-preview.html` 한 파일에 앱 전체(엔진 + 화면 + 폰트)가 들어 있어요. 네트워크나 다른 파일 없이 열리므로 Claude Code 파일 뷰어나 아무 브라우저에서 바로 실행됩니다. 한국어 전용 미리보기이며, `lib/core/coach_engine`과 같은 계산을 JS로 옮긴 것입니다(엔진을 바꾸면 `preview/src/app.html`도 함께 수정 → `python3 tool/build_preview.py`).

## 개발 명령어

```bash
flutter test                       # 엔진 + 상태 + 음식 추정 테스트
dart run tool/simulate.dart        # 시나리오 A~F 시뮬레이션 (특정 시나리오: ... A E)
```

## 구조

```
lib/
  core/coach_engine/   순수 Dart 엔진 (Flutter 의존 없음)
    constants.dart     모든 알고리즘 상수 (한 곳에서 수정)
    engine.dart        트렌드 EMA, Mifflin/Katch-McArdle, 실측 TDEE 역산, 블렌딩·스무딩,
                       목표 칼로리(안전 하한), 매크로, 신뢰도, 도달 예상, 체지방→목표체중, 근손실 경고
  data/                엔티티, repository 인터페이스 + 로컬 구현(shared_preferences), 텍스트 음식 추정
  state/app_state.dart ChangeNotifier 앱 상태 (체크인 호출, 샘플 데이터)
  ui/                  테마, 공용 위젯(링, 마스코트…), 화면
  l10n/                ARB (ko 템플릿, en)
tool/simulate.dart     시뮬레이터
test/                  단위 테스트
```

화면: 온보딩(동의 + 6단계) → 오늘 / 트렌드 / 주간 체크인 / 설정, 식사 기록 시트(텍스트·내 식사·직접 입력·사진[준비 중]), 체중 기록 시트.

## 시뮬레이션 결과 (seed 고정, 12주, 사용자는 매주 제안을 수락)

가상 사용자에게 "실제 소비량"(공식 대비 오차 포함), 일일 섭취 노이즈(σ 150 kcal), 수분 노이즈를 주고 엔진에 넣었습니다.

| 시나리오 | 설정 | ±150 kcal 수렴 | 안전 하한 | 비고 |
|---|---|---|---|---|
| A 감량 | 80kg, 체지방 20→15%, 보통, 공식이 200 kcal 과소추정 | **6주차** | 지킴 | 초반 2~4주는 EMA 지연으로 −200~−320 kcal 과소추정 |
| B 정체기 | 섭취 고정, 3주차부터 소비량 300 kcal 감소 | 8주차 | 지킴 | 9주차 `plateau` 판정 → 목표 하향 제안, 12주차엔 1,200 kcal 하한에 걸려 안내 |
| C 증량 | 65kg, 보통, 공식이 150 kcal 과대추정 | **3주차** | 지킴 | |
| D 기록 누락 | 식사 50%, 체중 35% | 5주차 | 지킴 | 12주 중 8주가 "신뢰도 낮음" → 목표 유지 (의도대로) |
| E 수분 변동 큼 | 체중 노이즈 σ 1.0kg | 12주차 | 지킴 | 오차가 ±200 kcal 안에서 흔들림. 수용 기준 **미달** |
| F 체성분 개선 | 60kg, 체지방 28→23% | **3주차** | 지킴 | |

- 수용 기준(4~6주 내 ±150 kcal): A·C·F 충족(테스트로 고정), B는 소비량이 도중에 변하는 시나리오라 8주, D는 데이터 부족 시 조정을 멈추는 게 정상 동작.
- **E 개선 후보:** 윈도우를 21일로 늘리기, 주간 변경 폭 ±100 kcal, 또는 추세 기울기를 회귀로 추정. 실제 사용자 데이터로 판단 필요.
- 감량 속도 상한(1.0%/주)은 *계획 속도*에 적용됩니다. E에서 추정 오차로 실제 한 주 감량이 1.04%가 된 주가 있었습니다.

## 가정과 결정

기획서의 기본값을 따랐고, 바꾸거나 새로 정한 것은 아래와 같습니다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 상태관리 | Riverpod 대신 `ChangeNotifier` + `InheritedNotifier` | MVP 규모에서 의존성 최소화. 화면이 늘면 Riverpod로 옮기기 쉬운 구조 |
| 라우팅 | go_router 대신 기본 `Navigator` + 하단 탭 | 화면 수가 적음 |
| 로컬 저장 | Drift 대신 `shared_preferences`(컬렉션별 JSON) | 웹에서도 설정 없이 동작. repository 인터페이스 뒤에 있어 Drift/Firebase로 교체 가능 |
| 체성분 개선 속도 | 감량 0.1 / 0.2 / 0.3 %/주 | 기획서에 값이 없어 느린 감량으로 가정 |
| 증량 속도 상한 | 0.5 %/주 | 기획서에 없음. 안전장치로 추가 |
| 활동계수 | 근력 + 유산소 횟수 합으로 매핑 | 기획서 표 기준 |
| 유효 기록일 | 하루 섭취 800 kcal 이상 기록된 날 | "기록 완성도 낮은 날 제외" 규칙의 구체화 |
| 윈도우 | 14일 기본, 기록이 적으면(70% 미만) 21일로 확장, 이력 10일 미만이면 실측 생략 | |
| β(실측 비중) | 전체 유효 기록일 ÷ 28 (최대 0.85) | 윈도우 내 일수로 하면 0.75를 넘지 못해서 |
| 신뢰도 | 낮음: 최근 7일 식사 <5일 또는 체중 <3회 / 높음: 식사 ≥6일 + 체중 ≥5회 / 나머지 보통 | "높음" 기준은 새로 정함 |

| 오늘 식사 | 체크인 계산에서 제외 (체중은 사용) | 하루가 끝나지 않아 섭취가 과소 집계됨 |
| 체크인 시점 | 현재 목표 시작 후 4일 이상 지난 첫 지정 요일 | 온보딩 직후 바로 체크인이 뜨지 않게 |
| 도달 예상 | 21일 이상 이력이면 최근 28일 추세 기울기, 아니면 계획 속도. ±20% 범위로 표시 | |
| 근손실 경고 | 최신 골격근량이 ~4주 전 측정 대비 1% 초과 감소 | |
| BMI 안전장치 | BMI < 18.5면 감량 목표 차단, 목표 체중 BMI < 18.5 차단 | |

## 3차: 운동 기록

- 종류(근력/유산소)와 시간만 기록해요. **운동 칼로리는 목표에 더하지 않아요.** 운동으로 쓴 에너지는 체중 추세에 이미 반영되어 실측 소비량(TDEE) 계산에 들어가므로, 더하면 이중으로 계산됩니다.
- 오늘 화면에 운동 카드, 주간 기록 카드에 '운동 N회'.
- 2주 이상 운동을 기록했고, 최근 2주 평균 횟수가 설정값과 달라 활동계수 구간이 바뀌면 체크인 화면에서 "기록에 맞추기"를 제안해요 (공식 추정치에만 영향, 실측 비중이 커질수록 영향 감소).
- 운동 시간은 1분 단위로 직접 입력하거나 ±1분, 자주 쓰는 시간(20/30/45/60/90분)으로 기록해요.
- **시간 기반 피드백** (`lib/core/coach_engine/workout_feedback.dart`, 무게 기록 없이): WHO 일반 권장(유산소 주 150분, 근력 주 2일 이상) 대비 진행도, 감량·체성분 목표일 때 근력 주 2일 권장, 최근 3주 평균 대비 증감(±30/60분), 설정 횟수 달성 여부, 7일 연속 운동 시 휴식 제안. 트렌드 탭에 최대 4개, 오늘 화면 운동 카드에 가장 중요한 1개를 보여줘요. 의학적 조언이 아닌 일반 가이드라인 기준이에요.
- 물 섭취 기록은 핵심 가치(주간 조정)와 무관하고 기록 부담만 늘어서 넣지 않았어요.

## 4차: 음식 검색 기록 (팻시크릿 방식)

- **직접 만든 음식 DB 221개** (`data/foods_ko.tsv` → `python3 tool/gen_foods.py` → 앱 `lib/data/food_db.g.dart` + 미리보기 `preview/src/foods.json`). 100g당 값 + 실제 1회 단위(1공기, 1줄, 1조각…). 일반적인 참고값이며 화면에도 그렇게 표시해요.
- 검색: 이름·별칭·영어, **초성 검색**(ㄷㄱㅅㅅ → 닭가슴살), 정확 > 앞부분 > 포함 순 정렬.
- 음식 상세: 단위(g 포함) 선택, 수량 0.5 단위·직접 입력, 칼로리·탄단지 실시간 계산, **아침/점심/저녁/간식** 중 선택해 추가. 추가 후 시트가 닫히지 않아 여러 개를 연속으로 기록할 수 있어요.
- 카테고리 둘러보기, 최근 먹은 음식, 목록에서 + 로 바로 추가, **내 음식 만들기**(1회 제공량 기준).
- 오늘 화면은 끼니별로 묶고 끼니 소계와 + 버튼을 보여줘요. 식사 수정에서 끼니도 바꿀 수 있어요.
- 텍스트 입력 추정도 같은 DB를 써요.
- **식약처 식품영양성분 DB 반영** (출처: 식품의약품안전처 식품영양성분 데이터베이스, 공공데이터포털 전국통합식품영양성분정보 표준데이터 API). 설정 › 정보에 출처를 표시해요.
  1. `DATA_GO_KR_KEY=... python3 tool/fetch_mfds_api.py` → `data/mfds_api_food.csv`(음식), `data/mfds_api_process.csv`(가공식품). 키는 환경변수로만 읽고 저장하지 않아요. API가 연결을 자주 끊어서 페이지(1,000건) 단위로 `data/.mfds_cache/`에 저장하고, 다시 실행하면 이어서 받아요. 원본 CSV와 캐시는 커밋하지 않아요.
  2. `python3 tool/import_mfds.py data/mfds_api_food.csv data/mfds_api_process.csv --include-processed` → `data/foods_mfds.tsv` (100g 기준으로 변환).
  3. `python3 tool/gen_foods.py` → 앱·미리보기 음식 DB. 직접 만든 221개가 같은 이름이면 우선이에요.
  - **음식**: 19,495건 중 이름 중복을 뺀 17,144개를 넣어요. 프랜차이즈 128개 브랜드(맥도날드·버거킹·스타벅스·메가커피·교촌 등) 메뉴가 모두 들어가요. 식약처 데이터에 없는 브랜드(bhc·네네·본죽 등)는 없어요. 프랜차이즈 메뉴는 이름 뒤에 업소명을 붙여요. 예: `빅맥 버거 (맥도날드)`.
  - 프랜차이즈 메뉴 상당수는 업체가 열량·단백질만 공개해요. 비어 있는 탄수화물·지방은 `data/foods_mfds.tsv` 9번째 열(`cf` 등)과 `Food.unknown`에 표시하고, 상세 화면에서 0g 대신 "—"와 안내 문구를 보여줘요(기록에는 0g으로 들어가요). `--full-macros-only`로 이런 행을 뺄 수 있어요.
  - **가공식품**: 전체 약 59만 건은 앱·미리보기에 넣기엔 너무 커서 대표식품명별 10개씩만 넣어요(`--processed-per-group`). 포장 중량이 있는 제품, 최신 데이터를 우선해요. 전체 검색은 서버 단계에서 API로 붙일 예정이에요.
  - 식약처 분류는 앱 분류(밥·죽, 반찬, 음료…)로 합쳤고, 피자·버거·샌드위치·치킨은 패스트푸드, 케이크·도넛 등은 간식·디저트로 옮겨요. 분류 둘러보기는 100개까지 보여주고 나머지는 검색으로 찾아요.
  - **Supabase(서버 검색, 준비 중)**: `supabase/schema.sql`(foods 테이블, 한글 부분·초성 검색 인덱스, 읽기 전용 RLS, `search_foods(q, lim)` 함수)을 SQL Editor에서 한 번 실행하고, `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY` 환경변수를 넣은 뒤 `python3 tool/load_supabase.py`로 전체(직접 만든 221 + 음식 1.7만 + 가공식품 28.9만, 원본 59만 건 중 식품코드가 같은 중복 제외)를 올려요. 로컬 PostgreSQL 16에서 검색 3~170ms 확인.
  - 바코드 스캔은 모바일 앱 + Open Food Facts/식약처 바코드 API로 검토.
